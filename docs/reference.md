# مرجع مصنع البرمجيات

المرجع الكامل: الوكلاء، والمهارات، والبوابات، والدروس، والتحديث. لطريقة التشغيل على مشروع جديد أو موجود، اقرأ [README](../README.md).

لكل مرحلة وكيلها الخاص، والوكلاء يعملون **بالتتابع** على كل مهمة. المنطق مبني على مهارات Matt Pocock (موجودة في `.claude/skills/`، رخصة MIT).

```
المخطط ─► [ لكل مهمة:  كاتب الاختبارات ─► 🔒 بوابة الاختبارات ─► المنفذ ─► البوابة الآلية ─► الفاحص ─► المدقق ─► المراجع ] ─► المراجع النهائي
              ▲            ▲                                    ▲                                  │         │         │
              │            └──── اختبارات خاطئة/ناقصة (FAIL_TESTS) أو اعتراض المنفذ (DISPUTE) ──────┘         │         │
              │                                                 └──────── خطأ تنفيذ (FAIL) ─────────┴─────────┴─────────┘
              └─────────────────────────────── خطأ في الخطة (FAIL_PLAN) ───────────────────────────────────────────┘
```

**القاعدة:** كل رفض يعود **لمن أخطأ**، ومعه شرح لموضع الخطأ وطريقة إصلاحه، ودرس يحفظه ذلك الوكيل حتى لا يكرر الخطأ.

## الوكلاء: وكيل لكل مرحلة

| المرحلة | الوكيل | مهارات Matt | المودل | مستوى التفكير | يكتب في |
|---|---|---|---|---|---|
| التوجيه | الموجّه `orchestrator` | — | sonnet | high | لا شيء (بلا أدوات كتابة) |
| الاكتشاف (معك) | جلسة الاكتشاف `discovery` | grill-with-docs، to-spec، to-tickets، prototype، research | opus | medium | المواصفات والمهام والمصطلحات والنماذج |
| تعديل الخطة | المخطط `planner` | grilling، domain-modeling، to-spec، to-tickets، codebase-design | opus | medium | المواصفات والمهام فقط |
| اختبارات القبول | كاتب الاختبارات `test-writer` | tdd، codebase-design | sonnet | high (يرتفع عند الإعادة إلى xhigh) | مجلد اختبارات المهمة الحالية فقط |
| التنفيذ | المنفذ `implementer` | tdd، codebase-design، diagnosing-bugs | sonnet | high (يرتفع عند الإعادة إلى xhigh) | الكود، وليس الاختبارات المقفلة |
| الفحص | الفاحص `tester` | tdd (الأنماط الخاطئة) | haiku | high | تقريره فقط |
| التدقيق | المدقق `auditor` | code-review (محور Standards) | sonnet | high | تقريره فقط |
| المراجعة | المراجع `reviewer` | code-review (محور Spec) | opus | medium | تقريره فقط |
| المراجعة النهائية | المراجع النهائي `final-reviewer` | code-review، pr | opus | medium | تقريره و`PR.md` |
| تحسين المصنع | وكيل التحسين `retro` | retro، writing-for-agents | opus | medium | تقريره، ثم ملفات المقترحات التي قبلتها فقط |
| تشخيص الأخطاء | المشخّص `diagnoser` | diagnosing-bugs، tdd | opus | medium (يرتفع عند الإعادة) | اختبار الانحدار للخطأ، وأدوات قياس مؤقتة يجب إزالتها |

وتوجد بوابتان من **كود** وليستا من وكلاء: بوابة الاختبارات بعد كاتب الاختبارات، والبوابة الآلية بعد المنفذ. كلتاهما لا تستهلك توكنز.

## المودل ومستوى التفكير لكل وكيل

كلاهما يُضبط من مكان واحد هو `factory/config.json`:

```json
"models": { "implementer": "sonnet", ... },
"effort": { "implementer": "high", "reviewer": "medium", ... },
"effortEscalation": { "enabled": true, "agents": ["implementer", "test-writer"], "max": "xhigh" }
```

- **القاعدة:** كل وكيل على Opus يفكر بمستوى medium، وكل وكيل على Sonnet أو Haiku بمستوى high.
- **المستويات:** `low` و`medium` و`high` و`xhigh` و`max`. كلما ارتفع المستوى زاد تفكير الوكيل قبل أن يجيب، وزادت التوكنز.
- **كيف يصل المستوى للوكيل:** `factory.mjs next` يحسب المودل والمستوى لكل خطوة، والموجّه يمررهما للوكيل. كل وكيل يحمل أيضًا قيمة افتراضية في ملفه داخل `.claude/agents/`.
- **التصعيد عند الإعادة:** إذا رُفض عمل المنفذ أو كاتب الاختبارات، يرتفع مستوى تفكيره درجة مع كل محاولة إضافية، حتى `xhigh`. مثال: المنفذ يبدأ بـ high، ثم xhigh من المحاولة الثانية. هكذا لا تُصرف توكنز عالية إلا حين تكون المهمة صعبة فعلًا.
- **لا يمكن تجاوزه:** الحارس يرفض أي تشغيل لوكيل بمودل أو مستوى غير الذي حدده المصنع.

## الموجّه (orchestrator)

الجلسة الرئيسية هي **الموجّه**، وهو وكيل له تعريفه الخاص في `.claude/agents/orchestrator.md`:

- **المودل:** sonnet بمستوى تفكير high.
- **أدواته:** تشغيل الوكلاء، والقراءة، والطرفية، والسؤال. **بلا أي أداة لكتابة الملفات**: يكتب الهدف وإجاباتك عبر `factory.mjs brief` و`answer`.
- **طرفيته محدودة بالحارس:** سكربتات المصنع وأوامر git للقراءة فقط.
- **لا يستطيع:**
  - تشغيل وكيل غير الخطوة الحالية،
  - تغيير مودل الوكيل أو مستوى تفكيره،
  - تعديل التعليمات التي يحددها المصنع للوكيل،
  - تخفيف أي رفض أو كتابة حكم بدل وكيل.

كل هذا مفروض بالحارس، وليس بالتعليمات فقط.

## صارمون ويعلّمون

كل وكيل يحكم على عمل غيره يتبع [factory/REVIEW-PROTOCOL.md](../factory/REVIEW-PROTOCOL.md):

**الصرامة**
- PASS يعني أن الوكيل فحص كل شيء في نطاقه ولم يجد ما يجب تغييره، وليس "مقبول تقريبًا".
- كل مشكلة جوهرية تعني FAIL، دون تهوين.
- يتحقق بنفسه (يشغّل ويفتح ويقرأ) ولا يثق في تقرير غيره.
- إن كان قد رفض المهمة سابقًا، يتأكد أولًا من إصلاح **كل** ملاحظة. الملاحظة غير المُصلحة رفض تلقائي.
- لا يختلق مشاكل: الملاحظة التي لا يمكن الإشارة إلى موضعها ليست ملاحظة.

**التعليم:** كل ملاحظة مكتوبة بالشكل نفسه:
```
- Where:   أين الخطأ (ملف:سطر، اختبار، أمر، أو سطر من المواصفات)
- Problem: ما الخطأ، مع الدليل
- Rule:    أي قاعدة كُسرت
- Fix:     التعديل المحدد الذي يصلحه
- LESSON:  جملة عامة يطبقها الوكيل في كل مهمة قادمة
```

**سجل الدروس (بالكود):**
- كل سطر `LESSON` يُحفظ في `factory/lessons/<الوكيل>.md` للوكيل الذي أخطأ.
- خطأ التنفيذ يُسجَّل للمنفذ، وخطأ الاختبارات لكاتب الاختبارات، وخطأ الخطة للمخطط.
- كل وكيل **يُوجَّه لقراءة دروسه قبل كل تشغيل**.
- الدروس **تبقى بين المشاريع**، فالمصنع يتحسن مع الوقت.
- إن تكرر درس سابق يُعدّ ويظهر في الداشبورد كـ"خطأ متكرر" (×2، ×3…)، والمراجعون يرفضون الخطأ المتكرر فورًا.
- بوابات الكود تعلّم أيضًا: كل رفض منها يحمل درسًا ثابتًا مناسبًا له.

## كيف نمنع التلاعب بالاختبارات

| الحيلة | كيف تُمنع |
|---|---|
| المنفذ يعدّل اختبار القبول لينجح كوده | الحارس يمنع الكتابة (عبر أدوات التعديل والطرفية معًا). وإن حدث بطريقة أخرى، تكشفه البصمة (hash) بعد التنفيذ فيُرفض. |
| المنفذ يحذف ملف اختبار | البوابة الآلية ترفض أي حذف لملف اختبار |
| المنفذ يعطّل اختبارًا (`skip` / `only` / `xit`) | البوابة الآلية ترفض |
| المنفذ يحذف تأكيدات (`expect` / `assert`) من اختبار قديم | البوابة الآلية تعدّ التأكيدات وترفض إن نقصت |
| كاتب الاختبارات ينسى معيارًا | بوابة الاختبارات تشترط سطر `COVERS` لكل معيار |
| اختبار شكلي ينجح دائمًا | بوابة الاختبارات تشغّله **قبل** التنفيذ ويجب أن يفشل. والفاحص يحكم على جودته ويرفضه بـ FAIL_TESTS. |
| المنفذ يرى اختبارًا خاطئًا | لا يعدّله، بل يعترض (DISPUTE)، فيقرر كاتب الاختبارات: يصلح الاختبار أو يشرح للمنفذ لماذا هو صحيح |

**ما لا يُضمن بالكود:** أن الاختبارات تغطي **كل** الحالات الممكنة. الموجود هو تغطية كل معيار قبول، وأن كل اختبار يفشل قبل التنفيذ، ثم حكم الفاحص على الحدود والحالات الخاطئة. قياس تغطية الكود واختبار الطفرات (mutation testing) غير مفعّلين بعد.

## كيف تبدأ

1. انسخ المجلد إلى جذر مشروعك، والأفضل أن يكون مستودع git.
2. **جلسة الاكتشاف** (أنت حاضر طوال الوقت):
   ```bash
   claude --agent discovery
   ```
   اكتب فكرتك، وأجب على جولات الأسئلة. في النهاية تكتب الجلسة المواصفات والمهام، وتنتهي بـ `plan-ready: OK`. أو من جلسة عادية: `/discovery <الفكرة>`.
3. **البناء** في جلسة جديدة:
   ```bash
   claude --agent orchestrator
   ```
4. افتح `factory/dashboard.html` في المتصفح. تتحدث اللوحة تلقائيًا كل 4 ثوانٍ، ولا تحتاج سيرفر.

## جلسة الاكتشاف

الاستجواب صار **حوارًا مباشرًا معك**، كما يوصي Matt Pocock، بدل أسئلة يكتبها وكيل في ملف.

- **المودل:** Opus بمستوى تفكير medium. Opus قوي بما يكفي، والتفكير المتوسط يوفّر التوكنز.
- **المسار، كله في سياق واحد غير منقطع:**
  1. **الاستجواب** (`grill-with-docs`، أي `grilling` مع `domain-modeling`):
     - جولات أسئلة، لكل سؤال إجابة مقترحة، وصيغته تجعل "نعم" قبولًا للمقترح.
     - الحقائق يبحث عنها الوكيل بنفسه ولا يسألك عنها.
     - المصطلحات والقرارات الصعبة تُكتب فورًا في `GLOSSARY.md` و`docs/adr/`.
  2. **منعطفات عند الحاجة فقط:**
     - **نموذج تجريبي** (`prototype`): للمنطق ملف واحد في `prototypes/`، وللواجهة فرع `prototype/<name>` منفصل عن فرع العمل.
     - **بحث موثّق** (`research`): يعمل في الخلفية ويكتب ملفًا بمصادره في `factory/discovery/research/`.
  3. **تأكيد الفهم المشترك** منك قبل كتابة أي شيء.
  4. **المواصفات** (`to-spec`): الميزات ونقاط الاختبار، وتؤكدها أنت.
  5. **المهام** (`to-tickets`): تراجع معك حجم كل مهمة وترتيب الاعتماد حتى توافق.
- **السجل:** كل جولة أسئلة وإجاباتك تُكتب في `factory/discovery/session.md`، فيقرؤها المخطط والمراجعون لاحقًا.
- **فحص `plan-ready` بالكود قبل أي بناء:**
  - المواصفات فيها الأقسام المطلوبة،
  - كل مهمة لها ميزة موجودة ومعايير قبول واعتماد صحيح بلا دوائر،
  - أوامر الفحص واختبارات القبول مضبوطة،
  - الجلسة لم تغيّر أي كود في فرع العمل.
  - إن فشل، يعرض كل المشاكل دفعة واحدة لتُصلح.
- **صلاحيات الجلسة (بالحارس):** تكتب الهدف والمواصفات والمهام وملاحظات الاكتشاف والمصطلحات والقرارات والنماذج فقط. لا تكتب كود المنتج، ولا تشغّل البناء.
- **لماذا جلسة جديدة للبناء:** كل وكيل في البناء يبدأ من الملفات وليس من المحادثة، وهذا ما يقصده Matt بأن كل تنفيذ يبدأ بسياق نظيف.
- **للتشغيل بلا حضورك:** ضع `"discovery": "planner"` في `config.json`، فيعود المخطط يكتب الخطة وحده ويسأل عبر الملفات.

## الداشبورد

شريط جانبي فيه أقسام اللوحة، وأعلاها اسم المشروع ومرحلته وجملة واحدة تقول ماذا يحدث الآن.

- **لوحة المهام (Kanban):**
  - كل عمود محطة يعمل فيها وكيل واحد. رأس العمود يذكر الوكيل ودوره ومودله ومستوى تفكيره، ويضيء حين يعمل.
  - كل صف ميزة، فيه شريط تقدّمها.
  - كل بطاقة مهمة، ولونها يوضح حالتها: تعمل الآن، أُعيدت للتصحيح ومن أعادها، تنتظر قرارك، أو منجزة.
  - المعيّنات على خط المحطات هي بوابات الكود.
  - الضغط على بطاقة يفتح لوحة جانبية فيها مراحل المهمة ورحلتها الكاملة ومعايير قبولها والدروس وتقاريرها.
- **مسار الإنتاج:** مخطط بالأسهم لمسار المهمة الحالية، مع أسهم الرفض والإعادة.
- **الوكلاء:** لكل وكيل المودل ومستوى التفكير والمهارات والنتائج والتوكنز والدروس.
- **التوكنز:** حسب الميزة والوكيل والمودل، وآخر التشغيلات.
- **الدروس:** دروس كل وكيل وتكرارها.
- **سجل الأحداث:** كل انتقال، مع تصفية حسب النوع.
- **الحماية والمهارات:** كل بوابة وعدد مرات عملها، ونسخة مهارات Matt.

تدعم اللوحة الوضع الفاتح والداكن، وتعمل على شاشة الهاتف.

## سير العمل عند تشغيل المصنع

1. **جلسة الاكتشاف معك**: الاستجواب ← نماذج تجريبية أو بحث عند الحاجة ← المواصفات مقسمة إلى **ميزات** ← وكل ميزة إلى **مهام** ← فحص `plan-ready`.
2. **الموجّه** في جلسة جديدة: يفحص تحديثات مهارات Matt، ثم يبدأ تشغيل المهام بالترتيب.
3. **لكل مهمة بالترتيب**:
   1. **كاتب الاختبارات**: اختبار قبول أو أكثر لكل معيار، في `tests/acceptance/<المهمة>/`.
   2. **بوابة الاختبارات (كود)**: لكل معيار اختبار؟ الاختبارات تفشل الآن؟ ← ثم تحفظها في commit وتقفلها ببصمة.
   3. **المنفذ**: يكتب الكود (مع اختباراته الداخلية بأسلوب TDD) حتى تنجح اختبارات القبول ← ثم commit.
   4. **البوابة الآلية (كود)**: commit موجود؟ لا ملفات معلقة؟ الاختبارات المقفلة لم تُمس؟ لا اختبار محذوف أو معطّل أو أُضعف؟ اختبارات القبول ناجحة؟ كل الفحوص ناجحة؟
   5. **الفاحص**: يشغّل كل شيء بنفسه، ويجرب كل معيار، ويحكم على جودة الاختبارات.
   6. **المدقق**: معايير المشروع وروائح الكود.
   7. **المراجع**: المطابقة مع المواصفات ← ثم إعادة تشغيل الفحوص مرة أخيرة بالكود ← المهمة منجزة.
4. **المراجع النهائي**: هل المهام معًا تسلّم المواصفات كاملة؟ أي نقص يتحول لمهام جديدة، وإلا يكتب `PR.md`.
5. **وكيل التحسين**: يقترح تحسينات للمصنع نفسه بالأدلة ← أنت تختار ما تقبله ← يطبّق المقبول فقط.
6. **أنت**: تراجع الفرع وتدمج أو تدفع بنفسك.

## مسار الأخطاء

حين تجد خطأً، في أي وقت بعد كتابة الخطة، حتى بعد التسليم، قل للموجّه ما حدث، أو استخدم:

```
/bug أدخلت 10 و20 فظهر المجموع 01020 بدل 30
```

**1. التسجيل:** يصير الخطأ مهمة من نوع `bug` في ميزة "إصلاح الأخطاء"، أو في ميزة محددة عبر `--feature F2`. الأخطاء تتقدم على أعمال الميزات المخططة. وإن كان المشروع قد سُلّم، يُعاد فتحه للإصلاح.

**2. المشخّص** (Opus، تفكير متوسط) يتبع مهارة `diagnosing-bugs` عند Matt Pocock بمراحلها:
- يبني أمرًا **يفشل بسبب هذا العَرَض تحديدًا**، ثم يعيد إنتاج الخطأ ويختصره إلى أصغر حالة.
- إن لم يستطع إعادة إنتاجه، يتوقف (`NEED_INFO`) ويطلب منك ما يحتاجه، مثل بيئة أو سجل أو خطوات. لا يخمّن بلا دليل.
- يكتب 3 إلى 5 فرضيات مرتبة، ويختبرها واحدة واحدة.
- قد يضيف أدوات قياس مؤقتة موسومة `[DEBUG-…]`. **يجب أن يزيلها كلها.** الكود يتحقق بعده أن الكود عاد كما كان، وأي بقايا توقف المصنع.
- يكتب **اختبار انحدار يفشل** بسبب الخطأ عند الـ seam الصحيح. إن لم يوجد seam صحيح، فهذا نفسه هو الاكتشاف (`SKIP`)، ويشرح لماذا، والمراجع يتحقق من ذلك.
- **لا يُصلح الخطأ أبدًا.** تقريره فيه أمر حلقة التشخيص، والسبب الجذري بالملف والدالة، واتجاه الإصلاح.

**3. بوابة الاختبارات** (كود) تتحقق أن اختبار الانحدار يفشل الآن، ثم تقفله.

**4. خط الإنتاج العادي:**
- **المنفذ** يصلح **السبب** لا العَرَض، ولا يستطيع تعديل اختبار الانحدار.
- **الفاحص** يشغّل حلقة التشخيص ويتأكد أنها نجحت.
- **المراجع** يتأكد أن الإصلاح عالج السبب الذي حدده المشخّص.

**5. الإغلاق:** بعد إصلاح الأخطاء يعود **المراجع النهائي** ليتأكد أن المشروع ما زال يطابق المواصفات. ولا تتكرر جولة تحسين المصنع.

**فصل الأدوار:** من يجد السبب ليس من يصلحه، ومن يصلحه لا يستطيع تغيير الاختبار الذي يثبت الخطأ. هذا الفصل نفسه الموجود بين كاتب الاختبارات والمنفذ.

## وكيل التحسين (Retro)

بعد أن ينجح المشروع في المراجعة النهائية، يعمل **وكيل التحسين**. هدفه أن يكون المشروع القادم أفضل، وذلك بتحسين **بيئة المصنع** وليس كود المنتج. مبني على مهارة `retro` عند Matt Pocock.

**1. الأرقام أولًا، بالكود:** `factory.mjs` يجمع ملف `factory/retro/facts.md` من سجل المشروع، فلا يصرف الوكيل توكنز في جمعها:
- كل رفض ومن رفض، مع روابط التقارير،
- فشل البوابات حسب نوعه،
- الاعتراضات وأخطاء الخطة،
- محاولات كل مهمة وتوكنزها،
- الدروس التي تكررت،
- التوكنز لكل وكيل،
- ما منعه الحارس، لأن كل منع يُسجَّل في `factory/guard-log.jsonl`.

**2. المقترحات (Opus، تفكير متوسط):** يقرأ الأرقام، ثم يفتح التقارير المهمة فقط، ويكتب `factory/retro/propose.md`. كل مقترح فيه: النوع، والأهمية، والدليل من هذا المشروع بالأرقام، والتعديل بالضبط، والملفات التي يمسّها. ويتبع قاعدة Matt:
- **الخطأ الميكانيكي** المتكرر يصير فحصًا آليًا (lint، أو أمر في `checks`، أو hook).
- **خطأ الحكم** يصير قاعدة في `CODING_STANDARDS.md` يطبّقها المدقق والمراجع.
- **درس تكرر** (×2 أو أكثر) دليل على أن الدرس وحده لم يكفِ.
- **حلقات الرفض المتكررة في مرحلة واحدة** تعني أن تعليمات ذلك الوكيل تحتاج قاعدة أوضح.
- **التوكنز:** إن صرف وكيل أكثر مما يحتاجه عمله، قد يكفي دليل تنقّل أو مودل أصغر. ولا يقترح أبدًا تخفيض مودل لوكيل رُفض عمله كثيرًا.
- إن سار المشروع بلا مشاكل، يقول ذلك ولا يقترح شيئًا.

**3. قرارك:** الموجّه يعرض عليك المقترحات، وتختار:

```bash
node factory/scripts/factory.mjs retro-accept R1 R2
```

(أو `all` أو `none`.)

**4. التطبيق:** يعود الوكيل ويطبّق **المقبول فقط**:
- **الحارس** يسمح له بكتابة ملفات المقترحات المقبولة وحدها، ويمنع أي ملف آخر.
- **فحص بعد انتهائه** يرفض أي ملف تغيّر خارجها.
- **الحفظ:** الكود يحفظ التغييرات في commit باسم `retro: apply R1, R2`.

**حدود ما يمسّه:** ملفات البيئة فقط: معايير الكود، `CLAUDE.md`، إعدادات lint وCI، تعليمات الوكلاء، `config.json`، وبروتوكول المراجعة. لا يمسّ كود المنتج ولا سكربتات المصنع. أي مقترح خارج هذه الحدود يُعلَّم "يحتاج تنفيذًا يدويًا".

**أين تراه:** في صفحة "تحسين المصنع" في الداشبورد: كل مقترح بدليله وحالته (مقترح، مقبول، طُبّق، رفضته، يدوي)، مع سجل المقترحات عبر كل المشاريع في `factory/retro/history.json`.

لإيقافه: `"retro": { "enabled": false }` في `config.json`.

## تحديث مهارات Matt Pocock

المصنع يستخدم آخر إصدار من المهارات، لكن **بتحكم**: لا يتغير سلوك الوكلاء أبدًا في منتصف مشروع.

- `factory/skills.lock.json` يثبّت رقم الـ commit من مستودع Matt، وبصمة كل مهارة، ومن يستخدمها من الوكلاء.
- عند كل `/factory` يفحص المنسق المستودع تلقائيًا، ويعرض عليك أي تحديث مع سبب التغيير، أو أي مهارة جديدة نشرها Matt.
- التحديث **يُرفض** أثناء مشروع قيد التنفيذ، ويُطبَّق بعد انتهائه.
- إذا عدّلت مهارة بنفسك، فلن يستبدلها التحديث إلا إذا طلبت ذلك صراحة.
- كل تحديث يُسجَّل في `factory/skills-changelog.md`.

```bash
node factory/scripts/update-skills.mjs check
```

```bash
node factory/scripts/update-skills.mjs apply
```

```bash
node factory/scripts/update-skills.mjs track retro --used-by "retro"
```

```bash
node factory/scripts/update-skills.mjs dismiss retro
```

## إحصاء التوكنز

hook من نوع `SubagentStop` يقرأ سجل كل وكيل بعد انتهائه، ويجمع توكنز الإدخال والإخراج والكاش، وينسبها للمهمة والوكيل والمحاولة. hook من نوع `Stop` يحسب توكنز المنسق نفسه. لعرض التكلفة بالدولار، املأ `prices_per_million_tokens` في `config.json` من صفحة الأسعار الرسمية.
